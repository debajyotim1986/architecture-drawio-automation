AI Atlassian Copilot — Architecture & Process Flow

How a Jira story file becomes a draw.io architecture diagram, end to end.

1. System architecture

The system is built around a strict boundary: only the MCP server ever touches .drawio XML. Copilot reasons about the story and the diagram topology, then issues intent-level tool calls; it never hand-edits XML. GCP icons are URL-encoded SVGs that Copilot embeds as data URIs in the node style strings it passes to add_node.

4. Key design decisions

DecisionWhy
AI never edits XML directly The MCP server is the single writer. Copilot speaks at the level of add this node, connect these two — not <mxCell>. Prevents malformed XML and keeps the prompt small.
Uncompressed .drawio XML Default draw.io files are zlib-compressed and base64-wrapped — unreadable in diffs and unparseable by the server. The MCP server reads/writes the uncompressed form so git diffs and tool mutations both work.
Stories are input-only No write_story tool exists. Stories represent the source of truth from Jira; the diagram is derived from them, never the reverse.
GCP icons embedded as URL-encoded data URIs Relative file paths fail in the VS Code drawio webview (sandbox blocks local loads). ;base64, data URIs are split by drawio's style parser on the literal ;. URL-encoded plain SVG is the format drawio itself emits — it has no ; to confuse the parser.
Stdio transport for MCP Local-only, no network surface, launched by VS Code per workspace. No auth needed.
