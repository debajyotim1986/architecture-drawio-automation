Write-back – end-to-end call flow

What happens, call by call, from the moment a user clicks “Write back” on a Looker dashboard until the new value is shown: Looker → Action Hub → Microsoft Entra → Apigee → ID&A → Write-back API → Writer API → BigQuery → back to Looker. Each step lists the endpoint, what is sent, what is checked, what comes back and what happens if it fails.

A · User and Looker steps 1–4

1User clicks the value and chooses “Write back”

User → Looker UI (browser, existing Looker session)

On a dashboard tile the user clicks a value of a field tagged writeback_key. The drill/actions menu shows Write back (listed by the Action Hub at registration, step P3).

Check: the action is visible only on tagged fields; the role “Writeback User” (send_to_integration) is needed to send.

2Looker asks the Action Hub for the form

Looker server → Action Hub · POST https://action-hub.looker-actions.svc.cluster.local/actions/writeback/form

Authorization: Token token="<looker-action-secret>"
{ "data": { "record_key": "ACC-1042", "field": "forecast_value", "current_value": "118000" } }

Action Hub checks the Looker secret and returns the form definition:

[ { "name": "new_value", "label": "New value", "type": "text", "required": true },
  { "name": "comment",   "label": "Comment",   "type": "textarea" } ]
If it fails: wrong secret → 401 → Looker shows “action unavailable”. Skipped entirely if the action has no form.

3User enters the new value and submits

User → Looker UI

Example: new value 125000, comment “Q4 update”. The browser never talks to the Action Hub – only the Looker server does.

4Looker sends the action to the Action Hub

Looker server → Action Hub · POST /actions/writeback/execute (inside the Looker cluster, ClusterIP + NetworkPolicy)

Authorization: Token token="<looker-action-secret>"
{ "type": "cell",
  "data": { "record_key": "ACC-1042", "field": "forecast_value", "value": "118000" },
  "form_params": { "new_value": "125000", "comment": "Q4 update" },
  "params": { "user_email": "jane.doe@lbg.example", "user_id": "2381",
              "writeback_allowed": "yes", "tenant": "tenant_a" } }

The params values come from Looker user attributes (liquid {{ _user_attributes['writeback_allowed'] }} etc.), so the user cannot change them.

B · Action Hub checks steps 5–6

5Check the Looker secret

Action Hub → Secret Manager · accessSecretVersion projects/looker-prj-int/secrets/looker-action-secret/versions/latest (Workload Identity as action-hub@; value cached in memory 5 min)

Compare the token in the Authorization header with the secret (constant-time compare).

If it fails: 401 to Looker; audit event ACTION_AUTH_FAILED.

6Check permission and payload, create the request id

  • writeback_allowed must be yes → otherwise 403, nothing else is called.
  • Required fields present: record_key, field, new_value, user_email, user_id.
  • Create request_id (UUID) – sent as X-Request-Id on every following call and used by the Writer to avoid duplicates.
If it fails: 403 “not allowed to write back” or 400 “missing field” returned to Looker; no token is requested.

C · Microsoft Entra token steps 7–8 · service identity, no user token

7Get a Google ID token for Entra

Action Hub → GKE metadata server · GET http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=api://AzureADTokenExchange&format=full (header Metadata-Flavor: Google)

Returns a Google-signed ID token for action-hub@: iss https://accounts.google.com, sub <unique id of action-hub@>, aud api://AzureADTokenExchange, valid 1 hour. This replaces a client secret.

8Call the Microsoft Entra token endpoint

Action Hub → Microsoft Entra · POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token (egress from the Looker cluster through the Spoke 2 proxy / NAT allow-list)

Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=<app id of looker-writeback-action-hub>
&scope=api://ida-token-exchange/.default
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<Google ID token from step 7>

Entra checks the app’s federated credential: issuer https://accounts.google.com, subject = unique id of action-hub@, audience api://AzureADTokenExchange. It then issues an app-only token:

{ "token_type": "Bearer", "expires_in": 3599, "access_token": "<Entra access token>" }
Cached: the Entra token is reused until about 5 minutes before expiry, so most clicks skip steps 7–8.
If it fails: AADSTS70021 (subject / audience mismatch) or network error → retry once, then 502 to Looker “write-back service unavailable”; audit ENTRA_TOKEN_FAILED.

The scope value is the Entra identifier of the ID&A exchange API – confirm the exact value with ID&A.

D · Apigee and ID&A token exchange steps 9–11

9Pass the Entra token to Apigee

Action Hub → Apigee · POST https://api-int.lloyds.internal/lloyds-auth-int/v1/token-exchange (Spoke 2 PSC endpoint → Apigee; TLS, internal CA)

Content-Type: application/x-www-form-urlencoded
X-Request-Id: 7f3c…

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<Entra access token>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=writeback-api
&scope=writeback.write

10Apigee checks the request and forwards it to ID&A

Apigee proxy lloyds-auth-int policy flow

  1. SpikeArrest 50 per second.
  2. Quota 600 per minute per client.
  3. VerifyJWT on subject_token: Entra JWKS signature, issuer https://sts.windows.net/<tenant>/, audience api://ida-token-exchange, not expired, appid = Action Hub app.
  4. Route to the ID&A token-exchange service.
If it fails: 401 (bad or expired Entra token) or 429 (quota) back to the Action Hub → Action Hub drops its cached Entra token, retries once from step 7, then 502 to Looker.

11ID&A issues the ID&A JWT

ID&A → Apigee → Action Hub

{ "access_token": "<ID&A JWT>", "token_type": "Bearer", "expires_in": 900 }

// decoded claims
{ "iss": "https://ida.lloyds.internal", "sub": "looker-action-hub", "aud": "writeback-api",
  "scope": "writeback.write", "exp": 1730000900, "kid": "ida-2026-10" }
Cached: the ID&A JWT is reused for about 14 minutes (expires in 15).

E · Write-back API steps 12–15 · new write-back cluster, Spoke 2

12Action Hub calls the Write-back API

Action Hub → Write-back API · POST https://writeback-api-int.internal/v1/writeback (internal LB in Spoke 2; only the Looker cluster pod range is allowed)

Authorization: Bearer <ID&A JWT>
X-Request-Id: 7f3c…
{ "request_id": "7f3c…", "tenant": "tenant_a", "record_key": "ACC-1042", "field": "forecast_value",
  "old_value": "118000", "new_value": "125000", "comment": "Q4 update",
  "actor_email": "jane.doe@lbg.example", "actor_id": "2381" }

13Verify the ID&A JWT

Write-back API → Apigee · GET https://api-int.lloyds.internal/lloyds-auth-int/v1/jwks (only when the key cache is empty or a new kid appears; cached 10 min)

Checks: RS256 signature with the key matching kid · iss = ID&A · aud = writeback-api · scope contains writeback.write · sub = looker-action-hub · not expired (60 s clock skew).

If it fails: 401 invalid_token → Action Hub drops its cached ID&A JWT, retries once from step 9, then 502 to Looker.

14Apply the write-back rules

Write-back API (rules from /config/writeback-rules.yaml)

  • Field forecast_value is writable; value is a number within 0 – 100,000,000.
  • record_key matches the allowed pattern; tenant is known.
  • Rate limit per user (30 per minute).
If it fails: 400 (invalid value) or 403 (field / tenant not allowed) → Action Hub returns the message to Looker; nothing is written.

15Get a Google ID token for the Writer

Write-back API → GKE metadata server · …/service-accounts/default/identity?audience=https://writer.internal&format=full

Returns an ID token for writeback-api@ with aud https://writer.internal.

F · Writer API and BigQuery steps 16–18

16Write-back API calls the Writer

Write-back API → Writer API · POST https://writer.writeback.svc.cluster.local/v1/write (ClusterIP; NetworkPolicy allows only Write-back API pods)

Authorization: Bearer <Google ID token>
X-Request-Id: 7f3c…
{ "request_id": "7f3c…", "tenant": "tenant_a", "record_key": "ACC-1042", "field": "forecast_value",
  "new_value": "125000", "actor_email": "jane.doe@lbg.example", "actor_id": "2381" }

Writer verifies the ID token with Google’s public certificates: aud = https://writer.internal, email = writeback-api@…, email_verified = true.

If it fails: 401 / 403 caller_not_allowed → 502 back up the chain.

17(Tenant-owned dataset only) impersonate the tenant writer

Writer → IAM Credentials · POST https://iamcredentials.googleapis.com/v1/projects/-/serviceAccounts/writer-tenant-a@tenant-a-data-prj.iam.gserviceaccount.com:generateAccessToken

Allowed because the tenant granted roles/iam.serviceAccountTokenCreator to writer@. Returns a 1-hour access token for writer-tenant-a@. Skipped for the platform-owned dataset.

18Insert the row in BigQuery

Writer → BigQuery · POST https://bigquery.googleapis.com/bigquery/v2/projects/lbg-data-prj-int/datasets/writeback/tables/writeback_log/insertAll (Private Google Access)

{ "rows": [ { "insertId": "7f3c…",
  "json": { "request_id": "7f3c…", "record_key": "ACC-1042", "field": "forecast_value", "new_value": "125000",
            "actor_email": "jane.doe@lbg.example", "actor_id": "2381", "written_at": "2026-10-27T06:46:11Z" } } ] }
Duplicates: the same request_id is used as insertId and checked by the Writer, so a retried click writes one row only.
If it fails: 500 from BigQuery → Writer retries with back-off (max 3 s) → 502 up the chain.

G · Back to the user steps 19–21

19Responses travel back

Writer → Write-back API → Action Hub

Writer → Write-back API : 200 { "status": "written", "request_id": "7f3c…" }
Write-back API → Action Hub : 200 { "status": "written", "request_id": "7f3c…" }

20Action Hub answers Looker

Action Hub → Looker server (response to step 4)

{ "looker": { "success": true, "refresh_query": true } }

On any failure: { "looker": { "success": false, "validation_errors": [ { "field": "new_value", "message": "…" } ] } } or a plain error message – Looker shows it to the user.

21Looker refreshes and the user sees the new value

Looker → BigQuery → User

Looker shows “Action sent successfully” and re-runs the tile query. The explore reads writeback.current_state (latest value per key and field), so ACC-1042 · forecast_value = 125000 appears on the dashboard.
