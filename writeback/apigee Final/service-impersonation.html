Service account impersonation – who runs each API and who owns each identity

When a tenant's dataset can be written only by the tenant's own service account, which identity runs the Action Hub, the Write-back API and the Writer API, and how does the write reach the tenant's table?

Short answer: both APIs run under platform service accounts owned by the Looker / BIaaS platform team, one set shared by all tenants. The tenant-owned service account is used only for the final BigQuery write: the Writer borrows it for that one call through service account impersonation, which the tenant grants.
The user's Looker login does not produce a JWT that is passed on. Looker only sends the user's identity (email, user ID, writeback_allowed) inside the action request. The JWT is obtained by the Action Hub for itself, through Apigee and ID&A, to prove that the call comes from Looker's write-back service.

Deployment layout

Looker, the Action Hub, the Write-back API and the Writer API all run in Spoke 2. Looker and the Action Hub run on the Looker GKE cluster. The Write-back API and the Writer API run on a separate write-back GKE cluster in the same spoke.

How step 5 works

  1. The Write-back API works out which tenant the request is for, from the caller registry or the target table, and calls the Writer with tenant = tenant_a.
  2. The Writer runs as writer@. Through Workload Identity it gets its own short-lived token, then asks Google for a token as writer-tenant-a@ (impersonation).
  3. Google issues that token only if the tenant has granted writer@ the role roles/iam.serviceAccountTokenCreator on writer-tenant-a@.
  4. The Writer appends the row to BigQuery with the tenant's token. BigQuery sees writer-tenant-a@ as the writer, so the platform's account never needs access to the dataset.

Reference code (Writer, Python)

import google.auth
from google.auth import impersonated_credentials
from google.cloud import bigquery

source, _ = google.auth.default()                      # writer@ via Workload Identity

def bq_client_for(tenant):
    target = f"writer-{tenant}@{TENANT_PROJECT[tenant]}.iam.gserviceaccount.com"
    creds = impersonated_credentials.Credentials(
        source_credentials=source,
        target_principal=target,
        target_scopes=["https://www.googleapis.com/auth/bigquery"],
        lifetime=600)                                     # 10 minutes, cached per tenant
    return bigquery.Client(project=TENANT_PROJECT[tenant], credentials=creds)

def write(tenant, request_id, rows):
    table = f"{TENANT_PROJECT[tenant]}.{tenant}.writeback_log"
    errors = bq_client_for(tenant).insert_rows_json(table, rows,
             row_ids=[f"{request_id}-{i}" for i in range(len(rows))])
    if errors: raise RuntimeError(errors)

Why this split

  • The tenant keeps control of its data. Only its own service account can write to its dataset, and it can revoke the token-creator grant at any time to cut off write-back immediately.
  • The platform runs one set of services, not one deployment per tenant. Onboarding a tenant means two grants on their side and a registry entry on ours.
  • A bug can't cross tenants. If tenant A's request were wrongly sent with tenant B's name, the Writer would try to act as writer-tenant-b@. The Write-back API checks the registry first, and every write is logged under the tenant's service account in BigQuery's audit logs.

What changes because both APIs are in Spoke 2 on a separate cluster

TopicEffect
Network path Action Hub → Write-back APIStays inside Spoke 2 – no HUB transit. Keep the internal load balancer, firewall rule (Action Hub range only) and TLS; the hop is cluster-to-cluster, not spoke-to-spoke.
Cluster separationLooker and Action Hub on the Looker cluster; Write-back API and Writer on the write-back cluster. A problem or upgrade on one cluster does not affect the other, and RBAC can differ per cluster.
Workload poolIf both clusters are in the same project, they share one workload pool (PROJECT.svc.id.goog). A KSA with the same namespace and name on both clusters would map to the same Google SA – so keep the namespaces distinct (looker-actions vs writeback) and never create a writeback/writer-ksa on the Looker cluster.
Workload Identity bindingsPROJECT.svc.id.goog[looker-actions/action-hub-ksa] → action-hub@; PROJECT.svc.id.goog[writeback/writeback-ksa] → writeback-api@; PROJECT.svc.id.goog[writeback/writer-ksa] → writer@.
Writer → tenant projectsImpersonation calls the IAM Credentials API; outbound access to Google APIs (Private Google Access) is needed from the write-back cluster. Check that VPC Service Controls perimeters, if used, allow it.
