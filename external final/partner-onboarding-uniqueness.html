How a new partner user is validated, stored and kept unique

When a partner company and its staff are onboarded, every user is validated by the onboarding job, stored once in the Tenant Registry, and kept unique by database rules – not by people being careful. The Looker key partner_id::tenant_id is built by the database, never typed in.

-- 1. One row per partner user (already in schema)
partner_id TEXT PRIMARY KEY

-- 2. Looker key generated by the database and unique (already in schema)
looker_external_user_id TEXT GENERATED ALWAYS AS (partner_id || '::' || tenant_id) STORED;
CREATE UNIQUE INDEX ux_partner_users_ext_id ON partner_users (looker_external_user_id);

-- 3. ADD: fixed formats – no ':' allowed, fixed case
ALTER TABLE tenants       ADD CONSTRAINT ck_tenant_id_fmt  CHECK (tenant_id  ~ '^[a-z0-9-]{2,30}$');
ALTER TABLE partner_users ADD CONSTRAINT ck_partner_id_fmt CHECK (partner_id ~ '^PRT-[A-Z0-9]{2,10}-[0-9]{4}$');

-- 4. Membership only once and only inside the user's own tenant (already in schema)
PRIMARY KEY (partner_id, looker_group_id)
FOREIGN KEY (tenant_id, looker_group_id) REFERENCES tenant_groups (tenant_id, looker_group_id)
CREATE TRIGGER partner_groups_tenant_guard BEFORE INSERT OR UPDATE ON partner_groups
  FOR EACH ROW EXECUTE FUNCTION check_partner_tenant();

-- 5. ADD: ids are never deleted or reused – offboarding sets status instead
REVOKE DELETE ON partner_users, tenants, partner_groups FROM onboarding;

7. Onboarding statement and outcomes

The onboarding job runs the whole onboarding in one transaction. The insert is safe even if two operators submit the same user at the same moment: the database lets one through and the other gets a conflict.

# Python (psycopg) – simplified onboarding job
def onboard_user(conn, req):
    pid, tid = req.partner_id.strip().upper(), req.tenant_id.strip().lower()
    require(req.ticket, "approval ticket missing")                         # gate 1
    if not re.fullmatch(r"PRT-[A-Z0-9]{2,10}-[0-9]{4}", pid):
        raise Reject("invalid partner_id format")                           # gate 3
    ida = ida_lookup(pid)                                                   # gate 4 – via Apigee
    if not ida or not ida.active or ida.org_code != tid:
        raise Reject("identity not found / inactive / wrong organisation in ID&A")
    with conn.transaction():
        t = conn.execute("SELECT status FROM tenants WHERE tenant_id=%s FOR SHARE", (tid,)).fetchone()
        if not t or t[0] != "active":
            raise Reject("tenant missing or not active")                    # gate 2
        row = conn.execute("""
            INSERT INTO partner_users (partner_id, tenant_id, kind, status, max_role, business_groups, updated_by)
            VALUES (%s, %s, 'human', 'active', %s, %s, 'onboarding')
            ON CONFLICT (partner_id) DO NOTHING
            RETURNING looker_external_user_id""", (pid, tid, req.max_role, req.business_groups)).fetchone()
        if row is None:                                                     # gate 5
            owner = conn.execute("SELECT tenant_id FROM partner_users WHERE partner_id=%s", (pid,)).fetchone()[0]
            if owner != tid:
                raise Escalate(f"{pid} already registered under tenant {owner}")
            ext_id = f"{pid}::{tid}"; status = "already exists – no change"
        else:
            ext_id, status = row[0], "created"
        for g in req.group_ids:                                             # gates 6 and 7 enforced by FK / trigger
            conn.execute("""INSERT INTO partner_groups (partner_id, tenant_id, looker_group_id, granted_reason, updated_by)
                            VALUES (%s,%s,%s,%s,'onboarding') ON CONFLICT DO NOTHING""", (pid, tid, g, req.ticket))
    return {"status": status, "external_user_id": ext_id}

8. What a rejected insert looks like

Even if someone bypasses the job and writes SQL directly, the database refuses bad data:

-- duplicate person
INSERT INTO partner_users (partner_id, tenant_id, kind, max_role, updated_by) VALUES ('PRT-ACME-0071','globex','human','viewer','x');
ERROR:  duplicate key value violates unique constraint "partner_users_pkey"
DETAIL: Key (partner_id)=(PRT-ACME-0071) already exists.

-- bad format (colon inside the id)
INSERT INTO partner_users (partner_id, tenant_id, kind, max_role, updated_by) VALUES ('PRT:ACME:71','acme','human','viewer','x');
ERROR:  new row for relation "partner_users" violates check constraint "ck_partner_id_fmt"

-- trying to set the Looker key by hand
UPDATE partner_users SET looker_external_user_id = 'someone-else' WHERE partner_id = 'PRT-ACME-0071';
ERROR:  column "looker_external_user_id" can only be updated to DEFAULT

-- membership in another tenant's group
INSERT INTO partner_groups (partner_id, tenant_id, looker_group_id, updated_by) VALUES ('PRT-ACME-0071','globex','22','x');
ERROR:  partner PRT-ACME-0071 does not belong to tenant globex

-- deleting a user to reuse the id
DELETE FROM partner_users WHERE partner_id = 'PRT-GLBX-0004';
ERROR:  permission denied for table partner_users

Onboarding makes the data right; the runtime checks make sure only that data is used.

Figure 4 – The key is read from the generated column, so the API and the database can never disagree
  1. The JWT sub must equal the X-Partner-Id header.
  2. That partner_id must exist with status active, and its tenant must be active.
  3. The tenant always comes from the registry row, never from the request.
  4. external_user_id is read from the generated column, never built in code.
  5. Looker keeps one embed user per external_user_id; the same key always returns to the same Looker user and a different key can never take it over.

11. Questions and answers

Can one person work for two partner companies?

Not with one partner_id: the primary key allows one tenant per id. ID&A should issue a separate id per company, which keeps their data fully separate in Looker as well.

Why not let the API build partner_id::tenant_id itself?

Two places building the same string can drift (case, spaces, separator). Reading the generated column means there is exactly one definition, enforced by the database.

What if two operators onboard the same user at the same time?

INSERT … ON CONFLICT DO NOTHING on the primary key: one insert wins, the other sees "already exists". There is no window for a duplicate.

Why never delete?

If a deleted id were given to a new person, Looker would recognise the old key and reuse the old embed user, including saved content and history. Disabling keeps audit history and prevents that.

Where is the format of the key fixed?

In the generated column definition. Fix it before go-live – changing it later creates new Looker users for everyone.
