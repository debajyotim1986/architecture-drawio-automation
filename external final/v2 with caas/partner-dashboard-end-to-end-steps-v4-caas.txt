PARTNER DASHBOARD ACCESS — END-TO-END STEPS (v4 · custom APIs on the CaaS cluster)
From onboarding a partner company to an external user seeing a row-filtered Looker dashboard.
Reference diagrams: partner-dashboard-flow-v6-caas-custom-apis.drawio (main architecture)
                    partner-dashboard-high-level-caas.drawio · partner-dashboard-behaviour-pattern-caas.drawio
Reference pages:    partner-onboarding-uniqueness.html   Schema: tenant_registry_schema.sql

What changed from v3
  - The three custom APIs (Token Validation, Partner Details, Embed URL) run on the CaaS GKE cluster
    (namespace partner-api) behind a CaaS internal load balancer.
  - The Looker API stays in the Spoke 1 Tooling GKE cluster and only orchestrates: it calls the CaaS APIs
    and chooses the landing dashboard.
  - The CaaS cluster never calls Looker directly. Both Looker calls go through the Reverse Proxy API door
    in Spoke 1 (https://looker-api.rp.internal/api/4.0):
      ① Partner Details API: POST /login (looker-ro)    then GET /folders/{id}/dashboards
      ② Embed URL API:       POST /login (looker-embed) then POST /embed/sso_url
  - ID&A is reached from the CaaS cluster through its own PSC endpoint to Apigee.

Numbering: 1, 2, 3 … is the action sequence; [4], [5.4a] … at the line end is the step badge on the diagrams.

Example values used throughout
  tenant_id            acme                      (our own identifier; nothing creates it for us)
  partner_id           PRT-ACME-0071             (= JWT sub, issued by ID&A)
  external_user_id     PRT-ACME-0071::acme       (partner_id::tenant_id, generated column in Cloud SQL)
  Looker groups        17 "Partner acme", 31 "Partner acme – Retail"      (ids assigned by Looker)
  Looker folders       512 Shared/Partners/acme, 530 Shared/Partners/acme/Retail  (ids assigned by Looker)
  Dashboards           42 Home, 43 Monthly Revenue (folder 512), 44 Retail KPIs (folder 530)
  Business group       retail
  Looker user id       2381                      (assigned by Looker at first login)


====================================================================================================
PART 1 — ONE-TIME PLATFORM SET-UP
====================================================================================================
   1a CaaS cluster (custom APIs)
1.  Create (or onboard to) the CaaS GKE cluster: private cluster, Workload Identity on
    (workload pool PROJECT.svc.id.goog), namespace partner-api.
2.  Create one Kubernetes service account per API and bind each to its own Google service account
    (roles/iam.workloadIdentityUser):
      token-validation-ksa -> token-validation@...iam   (no data access)
      partner-details-ksa  -> partner-details@...iam    (cloudsql.client, cloudsql.instanceUser,
                                                         secretAccessor on looker-ro only)
      embed-url-ksa        -> embed-url@...iam          (cloudsql.client, cloudsql.instanceUser,
                                                         secretAccessor on looker-embed only)
3.  Deploy the three APIs with a Cloud SQL Auth Proxy sidecar next to Partner Details and Embed URL
    (--private-ip --auto-iam-authn). No passwords or keys in YAML.
4.  Expose the APIs through one CaaS internal load balancer (paths /validate, /internal/partners/*,
    /internal/embed-url); allow ingress only from the Spoke 1 Looker API pod range (NetworkPolicy + firewall).
5.  Network paths to set up and test from the CaaS cluster:
      a. Spoke 1 Looker API -> CaaS internal LB (reachability per the chosen option: same VPC, via HUB, or PSC).
      b. CaaS -> Reverse Proxy API door looker-api.rp.internal (CaaS Cloud DNS peered to the Hub DNS;
         Reverse Proxy firewall allows the CaaS pod range).
      c. CaaS -> Apigee through a PSC endpoint in the CaaS VPC (ID&A only via Apigee).
      d. CaaS -> Cloud SQL private IP over Private Services Access.
   1b Tenant Registry (Cloud SQL)
6.  Create the Tenant Registry in Cloud SQL for PostgreSQL: private IP only, IAM database authentication on.
    Run tenant_registry_schema.sql (7 tables, triggers, roles).
7.  Create the database users through IAM:
      partner-details@...iam, embed-url@...iam -> DB role data_api   (SELECT only)
      onboarding@...iam                        -> DB role onboarding (write)
8.  How a CaaS API reaches Cloud SQL at run time:
      a. API connects to 127.0.0.1:5432 (the proxy sidecar).
      b. Proxy gets a token from the GKE metadata server (Workload Identity).
      c. Proxy fetches a short-lived client certificate from the Cloud SQL Admin API.
      d. Proxy connects to the instance private IP, TLS, IAM login.
      e. Rows come back; the API caches them for 60 seconds.
   1c Spoke 1 (Looker API + Reverse Proxy)
9.  Deploy the Looker API (orchestrator) in the Tooling GKE cluster. It holds no Looker keys and no DB access;
    it only knows the CaaS internal LB address.
10. Reverse Proxy (NGINX) keeps two doors:
      API door   looker-api.rp.internal  -> Spoke 2 Looker API 4.0 (internal callers: CaaS cluster)
      embed door External HTTPS LB       -> Spoke 2 Looker /login/embed, /embed/* (partner browsers)
   1d Looker and data
11. In Looker, create two API service users and store their client id / secret in Secret Manager:
      looker-ro     — lists folders and dashboards      (read by Partner Details API)
      looker-embed  — creates signed embed URLs         (read by Embed URL API)
12. In Looker Admin › User Attributes create tenant_id and business_group:
    string, user access None, hidden, no default value (no value = no rows).
13. In Looker Admin › Embed: signed embedding on; embedded domain allowlist = https://portal.partners.example.
14. Create Shared › Partners (no partner group gets access) and Shared › Templates (internal only).
15. In LookML add access filters to every explore the partner dashboards use:
      explore: orders {
        access_filter: { field: orders.tenant_id       user_attribute: tenant_id }
        access_filter: { field: orders.business_group  user_attribute: business_group }
      }
16. In BigQuery make sure every row carries tenant_id and business_group.

====================================================================================================
PART 2 — ONBOARD A TENANT (once per partner company)
====================================================================================================
17. Insert the tenant into the registry:
      INSERT INTO tenants (tenant_id, display_name, status, updated_by)
      VALUES ('acme', 'Acme Ltd', 'active', 'onboarding');
18. Create the tenant group in Looker (Admin › Users › Groups, or sdk.create_group).
    Looker assigns the id: 17 "Partner acme". Optionally 31 "Partner acme – Retail" for the retail business group.
19. Create the tenant folder under Shared › Partners, named after the tenant: acme -> Looker assigns folder id 512
    (and Retail inside it -> 530).
20. Lock each folder: switch off "inherit access", give View to its group only (512 -> group 17, 530 -> group 31).
21. Publish dashboards into the folders from Shared › Templates: copy (new id per tenant), move (keeps its id),
    or keep one shared dashboard in Partners/Common with View for every tenant group.
    Looker assigns the dashboard ids: 42, 43 in 512; 44 in 530.
22. Record the Looker ids in the registry:
      tenant_groups  ('acme','17','Partner acme','tenant'), ('acme','31','Partner acme – Retail','business_group','retail')
      group_folders  ('17','512','Partners/acme'), ('31','530','Partners/acme/Retail')
      UPDATE tenants SET home_dashboard_id = '42' WHERE tenant_id = 'acme';
23. Tag the tenant's data in BigQuery with tenant_id = 'acme' (and business_group values).


====================================================================================================
PART 3 — ONBOARD A PARTNER USER (once per external user)
====================================================================================================
24. ID&A creates the user's identity (userid, password, partner id PRT-ACME-0071) in OSIS.
25. Insert the user into the registry:
      INSERT INTO partner_users (partner_id, tenant_id, kind, status, max_role, business_groups, updated_by)
      VALUES ('PRT-ACME-0071','acme','human','active','analyst','retail','onboarding');
    PostgreSQL fills looker_external_user_id = 'PRT-ACME-0071::acme' automatically (generated column).
26. Grant the user's groups (this decides which folders, and therefore which dashboards, they can open):
      INSERT INTO partner_groups (partner_id, tenant_id, looker_group_id, granted_reason, updated_by)
      VALUES ('PRT-ACME-0071','acme','17','CHG-1001','onboarding'),
             ('PRT-ACME-0071','acme','31','CHG-1001','onboarding');
27. Nothing is done in Looker. The user does not exist in Looker yet, and admins never add external users
    to groups by hand. Every change is written to registry_audit by trigger.


====================================================================================================
PART 4 — LOGIN AND DASHBOARD LINK (Layer 1 — User & WebApp)                       steps 1 – 2
====================================================================================================
28. User logs in to the WebApp; ID&A issues the JWT (sub = PRT-ACME-0071, roles, names).          [1]
29. WebApp holds the session and the JWT.
30. User clicks "Open Dashboard".                                                                  [2]


====================================================================================================
PART 5 — WEBAPP CALLS THE LOOKER API IN SPOKE 1 (Layer 1 -> HUB -> Spoke 1)        step 3
====================================================================================================
31. WebApp calls the Looker API with three headers:
      Authorization: Bearer <JWT>
      X-Partner-Id:  PRT-ACME-0071
      X-Request-Id:  <uuid>          (carried on every later hop and log line)
    The caller never sends a tenant, a group or a folder.
32. Request leaves the WebApp through its PSC endpoint into the HUB VPC (Hub internal load balancer).
33. Hub Cloud Router has learned the Spoke 1 routes over BGP; the request goes through the HA VPN tunnel.
34. Request lands on the Looker API (orchestrator) in the Spoke 1 Tooling GKE cluster.


====================================================================================================
PART 6 — VALIDATE THE TOKEN (Spoke 1 -> CaaS Token Validation API -> Apigee -> ID&A)  steps 4 – 5.1
====================================================================================================
35. Looker API calls POST /validate on the CaaS internal LB with the JWT and X-Partner-Id.         [4]
36. Token Validation API calls ID&A through its PSC endpoint to Apigee (lloyds-auth-int);
    ID&A checks the token against OSIS. Deadline 2 s, one retry.                                 [4]
37. Token Validation API verifies the JWT with ID&A's public keys (JWKS, cached 5 minutes):
    signature, expiry, issuer, audience.                                                         [5.1]
38. X-Partner-Id must equal the JWT sub.                                                           [5.1]
39. Result to the Looker API: OK {sub, roles}, or
      401 invalid_token     -> WebApp shows "session expired, log in again"; flow stops.
      503 auth_unavailable  -> ID&A not reachable after the retry; flow stops (fail closed, never bypassed).


====================================================================================================
PART 7 — PARTNER DETAILS (Spoke 1 -> CaaS Partner Details API)                     steps 5.2 – 5.5
====================================================================================================
   5.2 – 5.3 Read the registry (one query)
40. Looker API calls GET /internal/partners/PRT-ACME-0071/details on the CaaS internal LB.         [5.2]
41. Partner Details API runs query Q1 through the Auth Proxy sidecar (steps 8a–8e):                [5.3]
      partner_users JOIN tenants JOIN partner_groups (valid today) JOIN tenant_groups (active) JOIN group_folders
    Result:
      partner_id PRT-ACME-0071 | tenant acme | external_user_id PRT-ACME-0071::acme
      partner active | tenant active | max_role analyst | business_groups retail | home dashboard 42
      looker_group_ids {17,31} | looker_folder_ids {512,530}
42. Unknown partner, disabled partner, suspended tenant or no active groups -> 403, flow stops (fail closed).
43. Effective role = JWT role capped at max_role; permissions and models come from role_capabilities.

   5.4a – 5.4 List what the user may open — ① via the Reverse Proxy
44. Partner Details API reads the looker-ro client id / secret from Secret Manager (Workload Identity).
45. ① It logs in through the Reverse Proxy API door:                                               [5.4a]
      POST https://looker-api.rp.internal/api/4.0/login  -> access token, cached ~1 hour (re-login on 401)
46. ① For each folder id (512, 530), through the Reverse Proxy:                                    [5.4]
      GET https://looker-api.rp.internal/api/4.0/folders/{id}/dashboards?fields=id,title,deleted
      (and /folders/{id}/children if sub-folders are used)
47. Path of every ① call: CaaS -> Reverse Proxy API door (Spoke 1) -> Cloud DNS peering (5a)
    -> HUB transit over HA VPN (5b) -> Spoke 2 internal LB -> Looker API 4.0, and back the same way.
48. Allowed dashboards = union of all folders: 42 Home, 43 Monthly Revenue, 44 Retail KPIs.
    No dashboards -> 403, flow stops. Reverse Proxy / DNS / Looker failure -> 502 with X-Request-Id.

   5.5 Return the details
49. Partner Details API returns to the Looker API:                                                 [5.5]
      partner_id, tenant_id, external_user_id, effective role, group_ids, folder_ids,
      business_groups, dashboards[], home_dashboard_id

   Choose the landing dashboard (Looker API, Spoke 1)
50. Looker API picks the one dashboard the signed URL will open:
      1) dashboard the user asked for — must be in the allowed list, otherwise 403
      2) tenants.home_dashboard_id
      3) dashboard titled "Home"
      4) lowest dashboard id
    Result: 42.


====================================================================================================
PART 8 — SIGNED URL (Spoke 1 -> CaaS Embed URL API)                                steps 5.6 – 5.11
====================================================================================================
51. Looker API calls POST /internal/embed-url on the CaaS internal LB with the details and dashboard 42.  [5.6]
52. Embed URL API checks again that dashboard 42 is in the allowed list (nothing is signed otherwise).    [5.7]
53. It reads the looker-embed client id / secret from Secret Manager (Workload Identity).
54. ② It logs in through the Reverse Proxy API door:                                               [5.8a]
      POST https://looker-api.rp.internal/api/4.0/login  -> access token, cached ~1 hour
55. ② It asks Looker to sign, through the Reverse Proxy API door (same 5a/5b path as ①):          [5.8b]
      POST https://looker-api.rp.internal/api/4.0/embed/sso_url
      {
        "target_url":        "https://analytics.partners.example/embed/dashboards/42?embed_domain=https://portal.partners.example",
        "external_user_id":  "PRT-ACME-0071::acme",
        "group_ids":         ["17", "31"],                       <- decides folders
        "external_group_id": "acme",
        "user_attributes":   { "tenant_id": "acme", "business_group": "retail" },   <- decides rows
        "permissions":       [ from role_capabilities ],
        "models":            [ "partner_analytics" ],
        "first_name": "Jane", "last_name": "Doe",
        "session_length":    3600,
        "force_logout_login": true
      }
56. Looker signs it with its embed secret and returns, back through the Reverse Proxy:            [5.9]
      { "url": "https://analytics.partners.example/login/embed/...&nonce=...&time=...&signature=..." }
    Single use, valid for a few minutes. The backend never opens, logs or stores it.
57. Embed URL API returns embed_url to the Looker API.                                             [5.10]
58. Looker API returns to the WebApp (Spoke 1 -> HUB -> PSC -> WebApp):                            [5.11]
      { embed_url, dashboards [42, 43, 44], home_dashboard_id 42, session_length 3600 }
59. WebApp builds its dashboard menu from dashboards[].


====================================================================================================
PART 9 — OPEN THE DASHBOARD (Stage 6 — browser, Looker in Spoke 2, BigQuery)      steps 6.1 – 6.4
====================================================================================================
60. WebApp sets iframe.src = embed_url; the browser opens it once                                  [6.1]
    (External HTTPS LB -> Reverse Proxy embed door -> HUB -> Spoke 2 internal LB -> Looker).
61. Looker checks the signature, time, nonce (no replay) and that the parent page is on the allowlist.  [6.2]
62. Looker looks up external_user_id "PRT-ACME-0071::acme":
      first login  -> creates an embed user and gives it its own id (2381), linked to this key for good
      later logins -> reuses user 2381
63. Looker sets the user's groups to exactly 17 and 31 (others removed) and sets
    tenant_id = acme, business_group = retail. This happens at every login.
64. Looker sets its session cookie and redirects to dashboard 42; it checks group 17 may view folder 512.
65. Every tile query gets WHERE tenant_id = 'acme' AND business_group = 'retail' (LookML access filter)
    and runs on BigQuery over private IP.                                                        [6.3]
66. Only acme / retail rows come back; dashboard 42 is shown in the WebApp.                        [6.4]
67. (Optional) A job copies Looker's user id 2381 into partner_users.looker_user_id for support.


====================================================================================================
PART 10 — SWITCHING DASHBOARDS (same session)
====================================================================================================
68. User clicks "Retail KPIs" in the WebApp menu (the menu belongs to the WebApp, not Looker).
69. WebApp sets iframe.src = https://analytics.partners.example/embed/dashboards/44?embed_domain=https://portal.partners.example
    — a plain link through the embed door; no new signed URL, no call to Spoke 1 or the CaaS cluster.
70. Looker recognises the session, checks that group 31 may view folder 530, and shows dashboard 44
    filtered to acme / retail.
71. A dashboard outside folders 512 / 530 is refused by Looker, even if the user types its id.
72. A new signed URL (Parts 5–9) is created only when the Looker session expires (3600 s) or the
    user logs in again.


====================================================================================================
PART 11 — CHANGING OR REMOVING ACCESS (applies at the user's next login)
====================================================================================================
73. Give an extra folder      -> INSERT a partner_groups row for that folder's group.
74. Take a folder away        -> set valid_to on that partner_groups row.
75. Change the rows they see  -> UPDATE partner_users.business_groups.
76. Block one user            -> partner_users.status = 'disabled' (Partner Details API returns 403).
77. Block a whole tenant      -> tenants.status = 'suspended'.
78. End an open session now   -> a Looker admin disables Looker user 2381.
79. Move a user to another tenant -> change partner_users.tenant_id; the key becomes PRT-ACME-0071::<new tenant>,
    so Looker creates a new user and old saved content stays behind.
80. A nightly job compares Looker folder permissions with group_folders and reports differences.


====================================================================================================
PART 12 — AUDIT AND MONITORING (runs throughout)
====================================================================================================
81. Every registry change is written to registry_audit by trigger (old and new row, who, when).
82. Every hop logs the same X-Request-Id. Audit events:
      Looker API             REQUEST_RECEIVED, LANDING_CHOSEN
      Token Validation API   AUTH_VERIFIED / AUTH_DENIED / AUTH_UNAVAILABLE
      Partner Details API    PARTNER_RESOLVED / ACCESS_DENIED
      Embed URL API          EMBED_URL_ISSUED (the URL itself is never logged)
      Reverse Proxy          ROUTE_FAILED (DNS, no route, Looker 5xx)
      Looker                 DASHBOARD_VIEW
83. ID&A sends authentication events, and Looker sends dashboard activity, to Cloud Logging.
84. Cloud Monitoring alerts on 401/403/5xx rates, latency (8 s request budget) and unusual activity.


KEY POINTS
- The caller sends only the JWT, partner id and request id. Tenant, groups, folders and row filters
  always come from the Tenant Registry.
- Looker API in Spoke 1 orchestrates; the three custom APIs run on the CaaS cluster and hold the keys
  (looker-ro, looker-embed) and the Cloud SQL access.
- The CaaS cluster never calls Looker directly: ① list dashboards and ② sso_url both go through the
  Reverse Proxy API door, Cloud DNS peering and the HUB to Spoke 2.
- Access chain: partner_users -> partner_groups -> tenant_groups -> group_folders -> Looker folder -> dashboards.
- group_ids decide which dashboards; user_attributes decide which rows.
- external_user_id = partner_id::tenant_id (PRT-ACME-0071::acme), a generated column; never change the format.
- Checked twice: the Embed URL API before signing, and Looker on every open and every switch.
- ID&A only through Apigee; Looker only through the Reverse Proxy; Spoke 1 to Spoke 2 always through the HUB.
- Fail closed: any failed check stops the flow with 401/403/502/503 and an audit event.
- Open item: how Spoke 1 reaches the CaaS internal LB (same VPC, via HUB, or PSC) — confirm and update step 5a.
