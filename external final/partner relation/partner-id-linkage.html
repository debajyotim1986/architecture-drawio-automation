Partner analytics · Embedded Looker on Google Cloud

How a partner ID is linked to groups, folders and dashboards

Every external user is identified by one partner ID. Through the Tenant Registry it resolves to a tenant, the tenant’s Looker groups, the folders those groups may open and the dashboards inside them – and to the row filters that limit the data to that tenant.

Partner ID→Tenant→Looker groups→Folders→Dashboards+Row filters
One identity

PRT-ACME-0071 is issued by ID&A and arrives as the token subject. It is the only value the caller supplies.

Groups decide which dashboards

A user reaches a dashboard only through group → folder → dashboard. There is no direct user-to-dashboard mapping.

Attributes decide which rows

tenant_id and business_group are applied as filters on every query in BigQuery.

2Which rows, and which Looker user

The same partner ID also decides the data filter and the Looker account. Tenant and business group are sent as user attributes in the signed embed URL; Looker adds them as filters on every BigQuery query. The external user ID ties the partner to one permanent Looker embed user.

3The data model behind the chain

The Tenant Registry holds every link. Looker generates the group and folder IDs; we copy them into the registry so one query can resolve a partner ID to everything it needs.

  TENANT_GROUPS ||--o{ PARTNER_GROUPS : "includes"

  }

Why this design. The caller never sends a tenant, group or folder – only the verified partner ID. Everything else comes from the registry, so access can be changed (add a folder, end a membership, suspend a tenant) with one row change, effective at the next login. Looker checks the folder permission on every dashboard open, and the row filters on every query.
