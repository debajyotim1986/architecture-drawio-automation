Quick glossary

Stays pinned while you scroll. Toggle with the button above.

SPA
Single-Page Application — the portal web app: one page loaded once in the browser; JavaScript updates it (renders tiles, swaps the iframe) without full page reloads.
iframe
An HTML "window inside the page" — the portal embeds Looker inside it. Setting its src loads a URL into that inner window only.
JWT
JSON Web Token — a signed identity "ticket" (who you are, your roles, expiry). Anyone can read it; nobody can alter it without breaking the signature.
JWKS
The public keys (at a URL) used to verify JWT signatures — so no shared secret is needed to check a token.
Bearer token
Sending a JWT as Authorization: Bearer … — "the bearer of this ticket is authorized."
SSO / signed embed URL
Single Sign-On. Here: a one-time, HMAC-signed Looker URL — opening it is the Looker login; no Looker password exists.
HMAC / signature
A cryptographic stamp made with a secret key; any change to the stamped data invalidates it.
nonce
A one-time random value inside the signed URL — makes it single-use (a second open fails).
Apigee
Google's API gateway — the guarded front door: rate-limits, verifies JWTs, forwards requests. Never talks to Looker here.
SpikeArrest
Apigee's rate-limiter — slows repeated attempts (the only brute-force control in this design).
WAF
Web Application Firewall — edge filter for malicious traffic. Deliberately absent here (flagged risk).
PSC
Private Service Connect — private Google-network wiring between services; no public internet path.
mTLS
Mutual TLS — both sides show certificates, so the API knows the caller really is Apigee.
GKE
Google Kubernetes Engine — the managed cluster running the UI app, the Data API, and Looker itself.
kubelet / probes
The per-node Kubernetes agent; it calls /healthz & /readyz to decide if a pod is alive and ready for traffic.
NetworkPolicy
Cluster firewall rules per pod — enforces "only Apigee reaches the API; only the API reaches Looker."
Workload Identity
Lets a pod act as a Google service account without any key file to steal or rotate.
Service account
A non-human identity for software (the API pod, the Looker→BigQuery connection).
Secret Manager
Google's vault for secrets (API keys, the embed secret, DB password) — fetched at startup, never in files.
Tenancy registry (BigQuery)
A dedicated BigQuery dataset holding the partner→tenant mapping — the authority the API consults (fail-closed; MERGE-only writes).
Tenant / multi-tenant
One partner organization; many tenants share one Looker while seeing only their own data.
Fail closed
On doubt or error → deny (403). Never guess a default — errors are the safe failure.
Allow-list
Explicit list of what's permitted; anything not on it is refused.
SDK
Software Development Kit — here looker_sdk: a Python library that calls Looker's REST API for you.
Reverse proxy
NGINX in front of Looker — the single internal doorway routing traffic to it.
Embed user
The Looker account it auto-creates per external_user_id on first signed login — no password, fully brokered.
external_user_id
Your stable key ("tenant::partnerId") that Looker allocates its own user against, forever.
User attribute
A per-user value stamped at login (here tenant_id) — the key row-level security filters on.
RLS / access_filter
Row-Level Security — LookML rule making Looker append WHERE tenant_id='…' to every query, invisibly.
LookML
Looker's modeling language — defines tables, joins, and the security filters, in version-controlled code.
Folder ACL
Access-Control List on a Looker folder — which groups may see its content; the dashboard-selection control after bootstrap.
HttpOnly cookie
A browser cookie JavaScript cannot read — safe carrier for the session token.
SameSite=None; Secure
Cookie settings allowing it inside a cross-site iframe, HTTPS-only — required for embeds.
WebSocket
A persistent two-way connection — Looker streams tile results over it (proxy must allow the upgrade).
CSP
Content-Security-Policy — the portal header that must whitelist the Looker host for the iframe (frame-src).
TTL cache
Remembered values that expire after a Time-To-Live (60 s tenant, 5 min dashboards) — speed without staleness.
ServiceCallout
An Apigee policy where the proxy itself calls another API mid-flow — how the one bootstrap call is made.

Flow.The 16-step flow — extended for Looker access (13–16 in full detail)

Steps 1–12 as agreed, then the part this runbook implements — 13 to 16 — broken down far enough that anyone can trace a click to a row of data and back.

Step 1 · the click and the front door

1a
User clicks the portal link (bookmark, email, or partner site). DNS resolves portal.yourdomain.com to the Global External HTTPS Load Balancer's anycast IP; the browser starts the TLS handshake against the LB's Google-managed certificate.
1b
Why this LB exists at all: it is required Apigee X plumbing — the external Application LB (L7) with a PSC Network Endpoint Group is how the Apigee X runtime is exposed on a custom hostname. (An L4 passthrough LB was evaluated and rejected — Apigee X exposure requires L7 + PSC NEG, and L4 would also lose HTTP routing and managed certs.)
1c
What is deliberately NOT here: Akamai and Cloud Armor were removed by decision — there is no edge WAF and no edge rate-limiting. Consequence: Apigee SpikeArrest (5b) is the only brute-force control in the whole chain — flagged risk, with Cloud Armor re-attachable later at this exact point with zero redesign.

Step 2 · Apigee external gateway — the only internet-facing surface

2a
The LB forwards through the PSC NEG to the Apigee external gateway proxy. Nothing else in the estate accepts internet traffic: not the UI app, not the internal proxy, not the GKE API, not Looker. Every request — human or machine — enters here.
2b
Route match decides the lane: GET /login and GET /static/** → the login-UI lane (no JWT required, step 3). /auth/login → the credential lane (step 5). /api/** → the JWT-protected data lane (step 11). Unknown paths → clean 404 at the gateway; nothing leaks southbound.

Step 3 · login page served from inside GKE

3a
Apigee proxies the /login request to the UI App hosted internally in GKE. The UI App is a private pod behind the internal gateway — it has no public IP and no internet route; only the Apigee path reaches it.
3b
The login page (HTML/JS/CSS) returns to the browser through the same chain. One app, two duties: it serves the login page now and will receive the submit next — there is no separate static bucket/CDN in this design.

Step 4 · the only manual action in the entire flow

4a
User types userid + password and presses Sign in. This is the single thing a human ever enters. Everything after — tenant, dashboards, identity, permissions — is derived server-side; the user never supplies or sees any of it.
4b
The submit leaves the browser as POST /auth/login over TLS to the same portal hostname — back through the LB into the Apigee external proxy. Credentials exist in transit only; the browser stores nothing.

Step 5 · front-door checks, then hand-off to the UI app

5a
The external proxy inspects the submit BEFORE credentials travel further: per-IP SpikeArrest (the brute-force control — see 1c), JSONThreatProtection (malformed/oversized payloads), and input validation (shape of userid/password fields).
5b
Failures die at the gate with clean faults — the request never reaches identity systems. Passes → the submit is forwarded to the UI App in GKE, which owns the next hop.

Step 6 · UI app → Apigee INTERNAL proxy

6a
From inside GKE, the UI App passes the credentials to the Apigee INTERNAL proxy. This proxy has no external hostname and no PSC exposure to the internet — the browser can never reach it directly, which is the point: the credential path from here on runs entirely on private networking.
6b
Why the chain goes back through Apigee at all: the internal proxy is the policy point for the identity leg — consistent fault mapping, logging, and one governed door in front of ID&A instead of ad-hoc service-to-service calls.

Step 7 · internal proxy → ID&A API

7a
The internal proxy calls the ID&A API (the identity team's service) with the credentials. Contract per Part 0.3: ID&A owns authentication only — it knows who the partner is, not which tenant they belong to.

Step 8 · ID&A validates against OSIS

8a
ID&A checks userid + password against the OSIS database — the credential store, and only a credential store: no tenant mapping lives there (that's the tenancy registry's job, step 13b).
8b
On failure, the result maps to clean faults on the way back — 401 bad credentials, 423 account locked, 503 auth service down — and the browser returns to the login form. Repeated failures are throttled by SpikeArrest (5a), not by an edge WAF (there is none, 1c).

Steps 9–10 · JWT minted — and it never detours to the browser

9a
✔ Valid → ID&A creates the signed JWT: claims are sub (the partner ID — the only identity field this design needs), roles, optional names, plus standard exp/iss/aud. No tenant_id claim — the Data API resolves that from its own registry at step 13b.
10a
The JWT travels back up the same private chain to Apigee — with NO browser detour. Apigee holds the token and continues the flow server-side toward the first dashboard render; the browser is still waiting on its login submit. (The HttpOnly cookie is set only at step 16a, on the dashboard response — not here.)

Step 11 · Apigee VerifyJWT — the gate every /api/** request passes forever

11a
Apigee's VerifyJWT policy validates the token: signature against ID&A's JWKS URI (public keys, so no shared secret), plus exp, iss, aud. Invalid/expired → 401 → the browser lands back on /login.
11b
This gate is permanent: the session-bootstrap call at each login and every ALT external-application call enter at exactly this step with a token. (Human dashboard clicks after login never come back here — they ride the live Looker session, 16b.) Login (1–10) is just the way humans obtain a token.

Step 12 · Apigee → GKE Data API — exactly ONE call per login

12a
Apigee strips ALL client-supplied identity headers (nothing the browser sent survives), then injects trusted headers from the verified claims — X-User-Id, X-Roles — purely informational: the API re-derives everything from the JWT itself (13a) and resolves tenant on its own (13b).
12b
The call goes out as Authorization: Bearer <JWT> over PSC/mTLS to the internal gateway fronting the Data API. The NetworkPolicy (B.21) makes this the only admissible path — no other pod, VPC peer, or internet source can reach the API. In the single-call pattern this request is GET /api/v1/session/bootstrap — the only Apigee→API call of the entire session. Hand-off complete: steps 13–16 below are what this runbook builds.

Step 13 · the API re-establishes trust — in code, not config

13a
JWT re-validated inside the pod (app/auth.py): signature fetched-and-cached from the JWKS URL, exp/iss/aud/sub required, roles claim must exist. Defense in depth — even if something ever bypassed Apigee, the pod refuses on its own.
13b
Tenant resolved from the tenancy registry (app/registry.py): get_tenant(sub) — one internal SELECT on the BigQuery tenant_registry dataset joining partner_users → tenants, cached 60 s per partner; with the single-call pattern this runs once per login, so BigQuery’s lookup latency never touches a click. Not an extra network hop in the flow; the JWT carries no tenant claim (OSIS doesn't know tenants — the registry is the authority).
13c
Fail closed: unknown partner, disabled partner, or suspended tenant → 403 partner not provisioned. Never a default tenant — an error is the safe failure. (Flipping a registry status is your ≤60 s kill switch.)

Step 14 · from claims to a one-time Looker key

14a
Dashboard resolved (app/looker.py): the tenant's Looker folder Partners/{tenant} is listed via the SDK (5-min cache). First render (no click yet) → the dashboard titled "Home", else the first in the folder. The allow-list governs this bootstrap selection; after bootstrap, dashboard switching is authorized by Looker folder ACLs (F.8/F.9) — see 16b.
14b
Capability chosen: roles[0] from the JWT → hardcoded ROLE_MAP → permissions + models. Unknown role → 403.
14c
The signed SSO embed URL is minted — sdk.create_sso_embed_url(...) with: external_user_id = "{tenant}::{sub}" (the identity Looker will allocate its own user for), external_group_id = tenant, user_attributes = {"tenant_id": tenant} (the RLS key), permissions/models, session_length=3600, force_logout_login=True. This call goes from the GKE API through the reverse proxy to Looker — Apigee is never involved with Looker in any direction. Looker signs the payload server-side with the embed secret and returns a URL valid for seconds, single-use (nonce). This is the programmatic twin of the embed URL a Looker admin can generate by hand in the Looker UI (a dashboard’s Embed / SSO-URL generator, or the docs’ sso-url tool) — same mechanism, but here it is minted automatically, per user, per login, at exactly this stage: inside the bootstrap, wire call POST /api/4.0/embed/sso_url (B.16b), before the bootstrap response is assembled. Nobody ever generates one manually in production.
14d
Returned upstream — the bootstrap payload: {tenant, dashboards[], home_dashboard_id, embed_url, navigation{embed_base, embed_domain, session_length}} → Apigee → browser. One response carries everything the portal will need for the whole session; the signed URL is never logged or cached anywhere.

Step 15 · opening the URL IS the Looker login

15a
The SPA sets the URL as the iframe src. The browser loads it against the public embed host → reverse proxy → Looker.
15b
Looker verifies the HMAC signature with the same embed secret, checks time/nonce (replay), and checks the parent origin against the Embedded Domain Allowlist (D.5). Any mismatch → refused frame.
15c
Identity allocation: Looker looks up external_user_id. First ever visit → it auto-creates an embed user (its own internal user_id, keyed to yours forever). Returning visit → same user matched, and groups/permissions/attributes are re-stamped from this login's payload (grant changes apply on next login). Auto-added to "Embed Group {tenant}" → which folder ACLs (F.8) recognize.
15d
Session opens in the iframe — Looker sets its session cookie (SameSite=None; Secure, E.1) and renders the requested dashboard shell.
15e
Every tile queries through RLS: tiles stream over WebSockets (E.3); for each query, the LookML access_filter binds orders.tenant_id to the user attribute — Looker itself appends WHERE orders.tenant_id = 'acme'. The user cannot see, remove, or bypass it; it applies to drill-downs, downloads and merges too.
15f
Data comes back private: the Looker connection runs as the single looker-bq-sa service account (jobUser@project + dataViewer@dataset only, F.2) against BigQuery / Cloud SQL over private IP. Only tenant-filtered rows flow up into the tiles.

Step 16 · the response, the cookie, and every request after

16a
The dashboard travels back: Looker → reverse proxy → (iframe content directly to the browser); the portal page around it came back through GKE API → Apigee → LB. On this response the portal's HttpOnly session cookie (carrying the JWT) is set — not earlier.
16b
Every dashboard switch after this is an iframe navigation — no Apigee, no GKE API, no new signed URL. The SPA sets iframe.src = navigation.embed_base + id + "?embed_domain=…" (values from the bootstrap payload). The browser already holds the Looker embed-session cookie (15d): Looker authenticates the navigation from the session, authorizes it via folder ACLs (the user's embed group can open only Partners/{tenant}, F.8/F.9), and RLS applies to every tile query exactly as in 15e. A hand-crafted id from another tenant's folder → Looker refuses the page.
16c
What still reaches the API after login: nothing. One bootstrap per login is the entire Apigee→GKE budget. ALT external applications are the exception by nature — each of their calls enters at step 11 with their own token. Registry suspension (13c) blocks a partner's next login within ≤60 s; it does not kill a live embed session — for an immediate hard kill, disable the embed user in Looker admin (the session dies on its next request).
16d
Expiry — aligned by design: session_length=3600 matches the JWT lifetime: one login buys one working hour. When the Looker session lapses, the iframe bounces to a login redirect; the SPA detects it (or the timer from navigation.session_length fires) and returns the user to /login — a fresh login repeats steps 1–16 and issues exactly one new bootstrap. Grant changes (new dashboards, role changes) therefore take effect at next login, not mid-session — an accepted trade of the single-call pattern.
ALT — external application: a system already holding a valid JWT (machine login with ID&A) calls /api/** through the same front door and joins at step 11; steps 1–10 are skipped. It can never call the GKE API directly — the NetworkPolicy admits only the Apigee path — and it passes the same registry + allow-list + RLS chain as a human. Machine partners need a partner_users row like anyone else.

Part B.GKE Data API — registry, code, deployment

The API is your own FastAPI microservice deployed in GKE (not Apigee config, not Looker). It is steps 13–14 of the flow: verify JWT → resolve tenant from the registry → resolve/validate dashboard → mint the signed embed URL. Only Apigee can call it.

                                                           └──(SDK, cluster-internal)──▶ Looker rp ──▶ Looker

gcloud secrets create looker-embed-secret      --replication-policy=automatic

B-3 · The tenancy registry (BigQuery) — partner → tenant mapping

Why this exists: OSIS holds credentials only — it does not map partners to tenants. This registry, owned by the Data API, is the authority for "which tenant does PRT-ACME-0071 belong to". Because that value becomes the RLS key, writes here get the same ceremony as an IAM change.
Is BigQuery fine for this? Yes — under three conditions. It fits because of the single-call pattern: one lookup per login + a 60 s cache makes BQ’s ~0.5–1 s point-lookup latency invisible, writes are onboarding-rare, and you run one data platform instead of adding a Cloud SQL instance. The conditions: (1) BigQuery enforces no keys or CHECKs — PRIMARY KEY … NOT ENFORCED is documentation, so ALL writes go through MERGE (duplicates impossible by construction), format validation moves to the write path, and reads treat a duplicate partner_id as an integrity breach (500 + alert), never "pick one"; (2) the registry lives in its own dataset tenant_registry, and the Looker connection SA gets no access to it; (3) if you ever move to per-request lookups or need sub-100 ms logins, swap back to Cloud SQL — get_tenant() is the one-file seam.

"""JWT re-validation (flow step 13 — defense in depth behind Apigee's step 11).

Identity comes ONLY from the verified token. Client-sent identity headers are
stripped by Apigee (5c) and ignored here regardless.
"""
import jwt
from fastapi import HTTPException, Request
from jwt import PyJWKClient

from . import config

_jwks = PyJWKClient(config.JWKS_URL, cache_keys=True, lifespan=300)


def verify_jwt(request: Request) -> dict:
    header = request.headers.get("authorization", "")
    if not header.lower().startswith("bearer "):
        raise HTTPException(401, "missing bearer token")
    token = header[7:]
    try:
        key = _jwks.get_signing_key_from_jwt(token).key
        claims = jwt.decode(
            token,
            key,
            algorithms=["RS256"],
            issuer=config.JWT_ISSUER,
            audience=config.JWT_AUDIENCE,
            options={"require": ["exp", "iss", "aud", "sub"]},
        )
    except jwt.PyJWTError as exc:
        raise HTTPException(401, f"invalid token: {exc}") from exc

    if not claims.get("roles"):
        raise HTTPException(403, "no roles claim")
    return claims

    """Default ('Home', else first) for first render; allow-list check otherwise."""
    allowed = tenant_dashboards(tenant)
    if requested_id is None:
        home = next((i for i, t in allowed.items() if t.lower() == "home"), None)
        return home or next(iter(allowed))
    if requested_id not in allowed:
        raise HTTPException(403, "dashboard not permitted for tenant")
    return requested_id


def build_embed_url(claims: dict, tenant: str, dashboard_id: str) -> str:
    role = claims["roles"][0]
    if role not in ROLE_MAP:
        raise HTTPException(403, "unknown role")
    rm = ROLE_MAP[role]

    resp = sdk.create_sso_embed_url(
        body=mdls.EmbedSsoParams(
            target_url=(
                # PUBLIC host — the browser opens this URL; the SDK itself
                # talks to Looker over LOOKER_BASE_URL (cluster-internal).
                f"{config.PUBLIC_LOOKER_EMBED_URL}/embed/dashboards/{dashboard_id}"
                f"?embed_domain={config.PORTAL_ORIGIN}"
            ),
            external_user_id=f"{tenant}::{claims['sub']}",
            first_name=claims.get("given_name", "Partner"),
            last_name=claims.get("family_name", "User"),
            external_group_id=tenant,
            user_attributes={"tenant_id": tenant},
            permissions=rm["permissions"],
            models=rm["models"],
            session_length=config.EMBED_SESSION_LENGTH,
            force_logout_login=True,
        )
    )
    return resp.url  # single-use, expires in seconds — return, never store/log

Part C.Row-level security — where WHERE tenant_id='acme' actually happens

You never write that WHERE clause. The registry-resolved tenant lands in user_attributes.tenant_id at embed login (B.16); a user attribute (C-1) plus a LookML binding (C-2) make Looker append the predicate to every query. Then you make coverage enforceable (C-3).

C-1 · Create the user attribute (Looker Admin, one time)

C.1

C.2

C.3
Why no default matters: with no default, a login that fails to set the attribute produces query errors, not another tenant's rows. Errors are the safe failure mode — the same fail-closed principle as the registry lookup (B.10).

Part E.Reverse proxy / GKE specifics that break embeds

Looker-in-an-iframe behind NGINX in GKE has three classic failure modes. Configure them up front.

E.1
Third-party iframe cookies: Looker's session cookie must be SameSite=None; Secure; the proxy must not strip/rewrite Set-Cookie. Symptom if wrong: iframe logs in, then instantly bounces or loops.
E.2
Forwarded proto/host: NGINX sends X-Forwarded-Proto: https + stable Host/X-Forwarded-Host; Looker's configured host URL matches what the iframe loads. Mismatch → redirect loops or signature failures.
E.3
WebSockets (tiles stream over WS): 
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 300s;

Missing → frame loads, every tile spins forever.

E.4
Body size & timeouts: raise client_max_body_size; proxy timeouts ≥ slowest expected query.
E.5
CSP on the portal: frame-src https://<public looker embed host> — the reverse direction of D.5's allowlist.
