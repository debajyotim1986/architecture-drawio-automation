Solution Architecture  ·  GCP / Apigee / GKE / Looker

External User Access to Looker on GKE via Apigee-Brokered Authentication

End-to-end design for exposing Looker dashboards (deployed as a container image in GKE, no GCP console access for users) to external consumers through an internet-facing Apigee entry point, a brokered login flow with the ID & Auth team, JWT enforcement, and internal routing to the GKE-hosted API and Looker via reverse proxy.

2.Layered View of the High-Level Flow

The same flow, decomposed into architectural layers — each layer has a single responsibility, a defined trust boundary, and explicit ingress/egress rules.

L0Client Layer — External User's Browser

Untrusted zone. Only ever talks to the public hostname (e.g. portal.yourdomain.com).

  • Runs the login SPA; holds JWT in memory or receives it as an HttpOnly cookie.
  • Never talks directly to the ID & Auth service, GKE, or Looker.
  • TLS 1.2+ enforced at the edge; HSTS returned by the load balancer.

L1Edge / Perimeter Layer — Apigee External Gateway Exposure

The only internet-facing surface: the Apigee external gateway proxy, exposed through the Global External HTTPS Load Balancer (required Apigee X plumbing for a custom hostname) with a PSC NEG backend.

  • Google-managed certificate, single public anycast IP, DNS mapped to it. No VM/GKE backend exposed here.
  • Akamai and Cloud Armor removed per architecture decision (v1.3). Consequence: Apigee SpikeArrest + JSON threat protection are the only brute-force/abuse controls on the login path — size them accordingly (tight per-IP limits on /auth/login, keyed on client IP from XFF).
  • Architect flag: Cloud Armor can be re-attached to this same LB later with zero redesign — recommended as low-cost insurance if login abuse is observed.

L2API Gateway Layer — Apigee (External Environment Group)

Policy enforcement point: routing, threat protection, JWT verification, quota, analytics.

  • Three logical proxies on one hostname: UI passthrough (/login, /static/*), auth broker (/auth/*), data API (/api/*).
  • SpikeArrest + JSON threat protection on the auth broker; VerifyJWT + claim extraction on the data API.
  • Strips all client-supplied identity headers before southbound routing; injects trusted headers (X-User-Id, X-Tenant-Id) from validated JWT claims.

L3Identity Layer — Apigee Internal Proxy → ID&A API → OSIS Database

Reached only via proxy chaining from the external Apigee proxy — the internal proxy, the ID&A API, and the OSIS database are never internet-exposed, and the browser can never call the internal proxy directly.

  • The Apigee internal proxy fronts the ID&A API: internal basepath, no external hostname binding, reachable only from the external proxy's chained call (and other internal consumers).
  • The ID&A API validates userid/password against the OSIS database (the credential store). Confirm with the ID&A team: passwords stored hashed + salted (bcrypt/scrypt/Argon2, never reversible), lockout counters in OSIS, and a least-privilege DB account for the API.
  • On success it returns JSON { jwt_token, expiry } and publishes a JWKS endpoint so Apigee verifies signatures with automatic key rotation.
  • Owns token TTL, refresh semantics, lockout policy, and revocation signals.

L4Internal Transport Layer — PSC / Internal LB (Southbound)

Private connectivity from Apigee's runtime into the workload VPC. No public GKE endpoints exist.

  • Apigee → Internal HTTPS LB (or PSC service attachment) → GKE Gateway/Ingress.
  • mTLS between Apigee target endpoint and the GKE ingress is the strong control; at minimum, firewall/authorized-network restriction so only Apigee can reach it.

L5Application Layer — GKE-Hosted API

Business/data API pod(s) in GKE. Trusts only Apigee-injected headers; optionally re-validates the JWT as defense-in-depth.

  • Maps the validated external identity to a Looker identity (embed user / API session).
  • Applies authorization: which dashboards, folders, row-level filters this user may see.
  • Runs with Workload Identity; secrets from Secret Manager, not baked into images.

L6Presentation Broker Layer — Reverse Proxy (NGINX/Envoy) in GKE

Fronts the Looker pods. Terminates internal TLS, normalizes headers, path-routes to Looker.

  • Network policy: accepts traffic only from the GKE API namespace/service account.
  • Handles Looker-specific requirements (WebSocket upgrade for render streams, cookie domain rewrites for embed).

L7Analytics Layer — Looker Instance (Containerized in GKE)

The Looker image deployed in GKE — no user access via GCP console; consumption is via embed/API only.

  • Signed SSO Embed or Looker API session generated by the L5 API after JWT validation.
  • Embed user attributes drive row-level security and content access per external user/tenant.

L8Data Layer — Backing Database(s)

Looker connects to the DB with its own service credentials over private IP.

  • Cloud SQL / BigQuery / other, reachable only on private networking (Private Service Access / private IP).
  • Row/column governance enforced in Looker's model + user attributes, not by handing DB credentials downstream.

XCross-Cutting — Observability, Secrets, Governance

  • Tracing: propagate a correlation ID from Apigee (X-Request-Id) through GKE API → reverse proxy → Looker logs; Cloud Trace + Cloud Logging sinks.
  • Metrics/alerts: Apigee Analytics for auth failure spikes; GKE workload metrics; uptime checks on the external hostname.
  • Secrets: Looker embed secret, DB creds, mTLS certs in Secret Manager; rotated; mounted via Workload Identity / CSI driver.
  • Audit: Cloud Audit Logs for infra changes; Apigee message logging (redact credentials/JWTs) for API-level audit.

3.Q1 — How can the login UI be exposed via Apigee?

Apigee is an API gateway, not a web server — but it can absolutely front a UI. Two clean options:

  • Option A (recommended): Build the login screen as a lightweight SPA (React/plain HTML+JS). Host the static assets in GKE (small NGINX pod) or a GCS bucket. Create an Apigee proxy (e.g., /login) whose target is that hosting backend. Apigee simply passes through the HTML/JS/CSS. The user hits https://portal.yourdomain.com/login — Apigee serves it via the target.
  • Option B: For a truly minimal screen, you can even return the HTML directly from an Apigee AssignMessage policy — but this is hacky and hard to maintain. Don't do this for anything real.

So the pattern is: one Apigee proxy for the UI passthrough (/login, /static/*), and separate proxies for the auth API and data API.

4.Q2 — Do you need an external Apigee gateway for users to hit?

Yes — one external entry point, but note the nuance:

  • Apigee X itself sits in a Google-managed tenant project. You expose it externally by putting a Global External HTTPS Load Balancer in front, with a Private Service Connect (PSC) NEG pointing to the Apigee instance. Attach Cloud Armor (WAF, rate limiting, geo rules) and a Google-managed cert on the LB.
  • You do not need two physically separate Apigee instances for "external" and "internal." Use one Apigee instance with two environment groups / hostnames: an external hostname (behind the external LB) for the login UI + auth endpoints, and the data-API proxies can live on the same instance — the "internal proxy" is logical (different basepath/proxy with JWT enforcement), not a separate deployment. This keeps cost and ops down.
  • If your security team mandates physical separation, then yes: external Apigee environment for UI/auth, and southbound traffic from Apigee to GKE goes over PSC or an internal LB — never a public GKE endpoint.

5.Q3 — How is the JWT supplied for user validation?

Split this into issuance and usage:

  • Issuance: The SPA POSTs credentials to https://portal.yourdomain.com/auth/login (an Apigee proxy). Apigee routes this to the ID & Auth team's service (ServiceCallout or as the proxy target). Their response JSON contains the JWT. Apigee returns it to the browser. Never let the browser call the ID team's service directly — always broker via Apigee so you can add threat protection, rate limiting on login attempts, and payload validation.
  • Storage on client: Prefer an HttpOnly, Secure, SameSite cookie set by Apigee (AssignMessage on the response) over localStorage — protects against XSS token theft. If the ID team's JWT must go in a header, the SPA holds it in memory and sends Authorization: Bearer <jwt> on every data call.
  • Validation: On every subsequent call, the Apigee VerifyJWT policy checks signature (against the ID team's JWKS URI or public key), exp, iss, aud, and any custom claims (tenant ID, role). Only after this does the request move southbound. Ask the ID team to expose a JWKS endpoint so key rotation is automatic — don't hardcode public keys.

6.Q4 — How does Apigee route the request to the login screen?

Conditional routing on the external proxy:

  • GET /login and GET /static/** → RouteRule targeting the UI hosting backend (no JWT check).
  • POST /auth/login → RouteRule targeting the ID & Auth validation service (no JWT check, but add SpikeArrest + JSON threat protection + optionally a CAPTCHA/bot check).
  • ANY /api/** → VerifyJWT flow first, then RouteRule to the GKE data API.

All three can be one proxy with conditional flows, or (cleaner) three proxies under one environment group sharing the same hostname. Unauthenticated hits to /api/** get a 401 from Apigee and the SPA redirects to /login.

7.Q5 — How does the login screen route to authentication, then to the internal path hitting the GKE API?

Sequence:

  1. User submits the form → SPA does fetch POST /auth/login (same Apigee hostname, so no CORS pain).
  2. Apigee applies input validation + rate limit → forwards to ID & Auth service → receives { "jwt": "eyJ..." }.
  3. Apigee sets the JWT as an HttpOnly cookie (or returns it in the JSON body) → SPA redirects user to the dashboard page.
  4. Dashboard page calls /api/dashboard/... with the JWT. Apigee's VerifyJWT policy authenticates it. Optionally use ExtractVariables to pull claims (user ID, tenant) and inject them as trusted headers (X-User-Id) southbound — the GKE API should trust only these Apigee-injected headers, stripped of anything client-supplied.
  5. Apigee routes southbound over PSC/internal LB to the GKE API service. Lock the GKE ingress so it accepts traffic only from Apigee (mTLS between Apigee and the reverse proxy is the strong version of this; at minimum, network-level restriction).
  6. The GKE API (or the NGINX/Envoy reverse proxy) forwards to Looker. For Looker, you'll typically exchange the validated identity for a Looker embed session (signed SSO embed URL) or Looker API token — external users shouldn't need native Looker credentials. This is where per-user row-level security in Looker gets enforced via embed user attributes.
Update (v1.4): the sequence above describes the general token model; the finalized flow refines the FIRST render — the JWT never detours to the browser (Apigee receives it from ID&A via the internal proxy, validates it, and calls the GKE API server-side with Bearer JWT), and the HttpOnly cookie is set on the dashboard response. Subsequent requests then follow steps 4–6 above unchanged. See the granular flow in Section 1 for the authoritative 16-step sequence.

8.Integration Details (Deep Dive)

The four integration seams that make or break this architecture, with the concrete contract at each seam.

8.1 Apigee ↔ ID & Auth Team

AspectContract / Recommendation
InterfaceREST POST /validate (or equivalent) — request: {userid, password} over TLS; response: {jwt_token, expiry, refresh_token?}.
ConnectivityProxy chaining: external Apigee proxy → Apigee internal proxy (internal basepath, never internet-exposed) → ID&A API → OSIS database. The browser never reaches the internal proxy or the API directly — the external proxy is the only entry.
Credential storeuserid/password persisted in the OSIS DB. Confirm: hashing (bcrypt/scrypt/Argon2), lockout counters, least-privilege DB account for the ID&A API, and private-network-only access to OSIS.
Key materialID team publishes a JWKS URI (/.well-known/jwks.json). Apigee VerifyJWT references it directly — key rotation needs zero Apigee redeploys.

Abuse controlSpikeArrest per client IP on /auth/login, JSONThreatProtection, optional reCAPTCHA Enterprise token verified in Apigee before forwarding credentials.

8.2 Apigee ↔ GKE-Hosted API (Southbound)

AspectContract / Recommendation
ConnectivityApigee southbound → PSC service attachment or Internal HTTPS LB in the workload VPC → GKE Gateway API / Ingress. GKE service type stays internal; no public endpoint ever.

8.3 GKE API ↔ Looker (via Reverse Proxy)

Consumption modelSigned SSO Embed (recommended for dashboards): the GKE API builds a signed embed URL using the Looker embed secret, mapping JWT claims → embed user + user attributes (external_user_id = sub, tenant_id attribute for row-level filters). Browser loads the dashboard in an iframe via the same trusted path.

8.4 Looker ↔ Database

AspectContract / Recommendation
ConnectivityPrivate IP only (Private Service Access for Cloud SQL, private BigQuery access). No public DB endpoints.
Authorization modelLooker connects with one service credential; per-user data isolation is enforced by Looker access filters / user attributes driven by the embed identity — not by minting DB users per external consumer.
PerformanceEnable Looker caching/PDTs for shared external dashboards; set per-tenant query limits to protect the DB from a single noisy tenant.

8.5 Session Lifecycle Across the Seams

  • Login: credentials → ID team → JWT (short TTL, e.g. 15–60 min) + optional refresh token.
  • Refresh: SPA calls /auth/refresh via Apigee before expiry; Apigee brokers to the ID team. Embed sessions in Looker have their own TTL — keep it ≤ JWT TTL so a revoked user can't outlive their token inside Looker.
  • Logout: Apigee clears the cookie, optionally writes the JWT ID (jti) to an Apigee cache/KVM deny-list until natural expiry, and the GKE API kills the Looker embed session.

9.2 Pipeline Stages (applies to every component)

  1. Build: compile/bundle; container images built by Cloud Build with provenance (SLSA) and signed (Binary Authorization attestation).
  2. Test: unit tests; for Apigee, apickli/newman integration tests against the dev env (login happy path, bad password, expired JWT, tampered JWT, missing token → 401).
  3. Scan: container vulnerability scanning in Artifact Registry; SAST/dependency scanning on SPA and API; policy checks (no plaintext secrets, no public services) via Terraform validators.
  4. Deploy to dev: automatic on merge to main. Apigee deploys a new proxy revision (instant rollback = redeploy previous revision).
  5. Promote to UAT: same artifacts, environment config swapped (Apigee KVMs / Helm values per env — target URLs, JWKS URI, cookie domain). Smoke tests + a scripted end-to-end: login → JWT → dashboard fetch.
  6. Promote to prod: manual approval gate. GKE API via canary (5% → 50% → 100% with automatic rollback on SLO breach); Apigee via revision cutover; SPA via versioned bucket path + CDN flip.

9.3 Environment & Config Separation

  • Apigee: dev / uat / prod environments in separate environment groups with distinct hostnames (portal-dev..., portal...). All env-specific values (auth service URL, JWKS URI, southbound target) live in per-env KVMs or Terraform-managed target servers — proxy bundles stay identical across envs.
  • GKE: separate clusters (or at minimum namespaces + separate node pools) per env; Helm/Kustomize overlays carry env differences.
  • Secrets: Secret Manager per project/env; CI service accounts have least-privilege deployer roles only (e.g. roles/apigee.environmentAdmin scoped, roles/container.developer).

9.4 Release Safety Nets

  • Rollback: Apigee = previous revision redeploy (seconds); GKE = Cloud Deploy/Argo rollback to prior image; SPA = repoint CDN to previous bucket version.
  • Contract tests: a small pact-style suite pinning the ID team's response schema and the JWT claims contract — pipeline fails if the auth team changes the contract unannounced.
  • Post-deploy verification: synthetic login journey (test user) runs after every prod deploy and on a schedule; alerts on failure.
  • Drift control: GitOps (ArgoCD) or scheduled terraform plan detects out-of-band changes to LB/Armor/Apigee config.
Principle: the artifact that passed tests in dev is byte-identical to what runs in prod — only configuration (KVM values, Helm values, Terraform vars) changes per environment.

10.Architect's Flags & Recommendations

A few things I'd flag as an architect:

  • Don't double-authenticate ambiguously. Decide clearly: Apigee is the only JWT enforcement point, and everything behind it trusts Apigee via network + mTLS. Re-validating the JWT in the GKE API is fine as defense-in-depth, but define it explicitly.
  • Looker embedding is the real design decision. If users see dashboards in a browser, you almost certainly want Looker Signed SSO Embed — your GKE API generates the signed embed URL after JWT validation, mapping the JWT claims to Looker embed user attributes. That's cleaner than proxying raw Looker traffic through the API.
  • Session lifecycle: define JWT TTL, refresh strategy (refresh token vs re-login), and logout (cookie clear + optional revocation list in Apigee via cache).
  • Cloud Armor on the external LB is non-negotiable for an internet-exposed login — brute-force and credential-stuffing protection at the edge, plus Apigee SpikeArrest per-IP on /auth/login.
Open decisions to confirm: Apigee X vs Hybrid; embedded dashboards vs API-driven data pulls; physical vs logical separation of external/internal Apigee environments; JWT storage model (HttpOnly cookie vs in-memory + header). These determine the exact PSC/mTLS wiring on the southbound leg.
